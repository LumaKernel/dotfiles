新しいタスクや差し込みの要望を受け取り、それを適切に分解・計画してプロジェクトのタスク管理に組み込む。
「局所的にコードを変えて終わり」ではなく、影響範囲を多面的に分析し、必要な変更をすべて洗い出してからタスクとして記録する。

## 入力

ユーザーからタスクの説明を受け取る。曖昧な場合は質問して明確にする。

## 手順

### 0. 構造的根本原因分析（Structural Root Cause Analysis）

タスク分解や影響分析の**前に**、まず以下を考える:

#### この問題は構造の問題か？

- **同じクラスのバグが他でも起きうるか？** 今回のインスタンスだけでなく、同じパターンの問題が構造的に存在しないか
- **そもそもこの構造/やり方が間違っていないか？** 対症療法でなく、問題を不可能にする設計変更がありうるか
- **既存のツール・言語機能・パターンで自動的に防げないか？** TypeScript の型システム、lint ルール、既存の CI ツール、言語の標準機能など

#### 対策の評価基準（決定論的で自動的か？）

提案する対策は以下の順で優先する:

1. **構造変更で問題自体を不可能にする** — 最優先。例: 型チェック境界に入れる、レイヤーを統合する
2. **言語・ツールの既存機能で自動検出** — 例: `tsc --checkJs`, JSDoc `@satisfies`, exhaustive check, lint rule
3. **自動テストで検出** — CI で確定的に検出。ただしテストは「構造が壊れている」ことを認めた上での安全網
4. **手動チェックリスト・ルール文書** — 最も弱い。人間が忘れたら無意味

**偽の安心感に注意:** 手動メンテが必要なリスト、網羅性を保証しない型注釈（例: `(keyof T)[]` は部分集合でも通る）、実行されないかもしれないチェックは「対策した気になるだけ」になりがち。本当に決定論的に防げるかを厳密に評価する。

#### 文書化

構造的問題を発見した場合は、対症療法タスクとは別に:
- 根本原因と構造的修正案を設計ドキュメントに記録する
- 長期的な構造改善タスクと短期的な安全網タスクを区別して両方記録する

### 1. 影響分析（Impact Analysis）

タスクの内容を受け取ったら、まず以下の全観点で影響を洗い出す:

#### コード影響

- **直接変更が必要なファイル**: Glob/Grep で該当コードを特定
- **間接的に影響を受けるファイル**: 型定義の変更による波及、import 元の変更
- **exhaustive check への影響**: union型やswitchに新バリアントが追加されるか
- **テストの変更・追加**: 既存テストの修正が必要か、新規テストが必要か

#### 設計影響

- **設計ドキュメントの更新が必要か**: アーキテクチャ、コーディング規約、ページ設計など
- **型定義の追加・変更**: 共有型への影響
- **レイヤー構造への影響**: 責務分離は正しいか
- **データフロー**: 永続化・API のデータ構造に影響があるか

#### 品質影響

- **テスト戦略**: 新しいテストが必要な箇所はどこか（ユニット/統合/Storybook）
- **Storybook**: 新しい story が必要か、既存 story の更新が必要か
- **カバレッジ**: カバレッジ低下を防ぐために必要なテストは何か
- **a11y**: アクセシビリティに影響があるか（キーボード操作、スクリーンリーダー、コントラスト）

#### メタ戦略影響

- **メタ戦略・開発規約ドキュメントの更新が必要か**: 新しい開発パターンや品質ゲートの追加
- **CLAUDE.md の更新が必要か**: プロジェクト全体の指針に影響するか
- **人間の判断が必要な事項はあるか**: あれば所定の場所に記録する

### 2. タスク分解（Task Decomposition）

影響分析の結果をもとに、タスクを作業単位に分解する。

#### 分解の原則

1. **1タスク = 1コミット可能な単位** にする
2. **依存関係を明示** する（「Xの後にY」「XとYは並行可能」）
3. **型定義を先行タスクに** する（型が決まれば独立実装が可能になる）
4. **設計変更は実装の前に** する（Document-Driven Development）

#### タスクの種類を分類

各タスクに以下のラベルをつける:

- `[設計]` — design/ 配下のドキュメント更新
- `[型]` — 型定義の追加・変更
- `[ロジック]` — 純粋関数・ドメインロジック
- `[UI]` — コンポーネント・ページ
- `[テスト]` — テスト追加・修正
- `[story]` — Storybook story
- `[a11y]` — アクセシビリティ対応
- `[メタ]` — メタ戦略・規約の更新
- `[QA]` — 品質チェック・検証

### 3. タスクリスト更新

プロジェクトのタスク管理ファイル（CLAUDE.md やプロジェクト構造から特定する）に分解したタスクを追記する。

#### 挿入場所の判断

- 既存セクションに属するタスクなら、そのセクション内の適切な位置に追加
- 新しいカテゴリが必要なら、セクションを新設
- 「差し込みタスク」セクションが適切な場合はそこに追加
- **ステータスは未着手で追加する**（勝手に実装しない）

#### 記述フォーマット

```markdown
- [ ] タスク名 (具体的な内容の要約)
  - [設計] design/xxx.md 更新: yyy
  - [型] types.ts に zzz 追加
  - [ロジック] xxx.ts 新規: yyy
  - [テスト] xxx.test.ts: テストケース N 件
  - [story] XxxComponent.stories.tsx 追加
  - [a11y] キーボード操作対応
  - [メタ] meta-strategy.md 更新: yyy
```

サブタスクが不要な小さいタスクは1行で書いてもよい。

### 4. 依存関係・順序の整理

分解したタスクの実行順序を整理する:

- **先行タスク**: 他のタスクがブロックされるもの（型定義、設計文書など）
- **並行可能タスク**: 互いに独立して実装できるもの
- **後続タスク**: 他のタスクの完了を待つもの（統合テスト、QAなど）

依存があればタスク管理ファイルに注記する。

### 5. リスク・ブロッカーの識別

- **人間の判断が必要** → 所定の場所に記録（プロジェクトの慣習に従う）
- **外部依存がある** → タスクに「— 外部依存」と注記
- **破壊的変更の可能性** → 影響範囲を明記
- **パフォーマンスリスク** → 検証計画をタスクに含める

### 6. 報告

以下を報告する:

- **タスク概要**: 何をどう変えるか（1-3文）
- **影響範囲**: 影響を受けるファイル・モジュールの一覧
- **分解結果**: タスク一覧と依存関係
- **戦略的変更**: 設計文書やメタ戦略への変更があれば明記
- **リスク・ブロッカー**: 人間の判断が必要な事項

## 注意事項

- **実装はしない**: このスキルはタスクの分析・計画・記録のみ。実装は別途行う
- **過不足なく**: 影響がないのに無理に全観点を埋めない。影響がある箇所だけ記載する
- **既存タスクとの重複チェック**: タスク管理ファイルを読み、既に同様のタスクがないか確認する
- **コミットはしない**: タスクリスト更新後のコミットはユーザーに確認する
