ブラウザ上で実際に発生・再現できているバグを調査し、修正する。

## 前提

このスキルは以下の状況で呼び出される:

- 呼び出し者の手元のブラウザで、バグが今まさに再現できている
- コードベースは十分に複雑で、ソースコードを読むだけでは原因特定が困難
- DOM の状態、React/フレームワークの内部状態、CSS の計算値、イベントの発火状況など、ランタイムの実態を知る必要がある

したがって、ソースコードの静的解析だけに頼らず、呼び出し者のブラウザコンソールでスクリプトを実行してもらい、その出力を受け取ることで状況を把握する。

## 手順

### 1. 状況ヒアリングと調査方針の決定

バグの概要を聞き、以下を判断する:

- playwright-cli を並列で使うか？
  - そのプロジェクトで playwright-cli の利用が標準化されている場合（CLAUDE.md や設定に記載がある、普段から使っている）→ 聞かずに並列で使う
  - そうでない場合 → 「playwright-cli でも並列して検証しますか？」と確認する
- 関連しそうなコンポーネント・ファイルの当たりをつける

### 2. コンソールスクリプトの作成と実行依頼

何回もやりとりしなくて済むように、1回で網羅的な情報を取得するスクリプトを書く。

スクリプト設計の原則:

- 決め打ちしない: 特定のセレクタやコンポーネント名に依存せず、周辺を探索的に取得する
  - 例: `querySelector` で1要素だけ取るのではなく、`querySelectorAll` で周辺ノードも含めて取得する
  - 例: 対象要素の親・兄弟・子も含めて構造を出力する
- 複数の観点を1スクリプトに含める:
  - DOM 構造（対象要素とその周辺）
  - 計算済みスタイル（`getComputedStyle`）
  - データ属性・ARIA 属性
  - React/フレームワークの内部状態（`__reactFiber$`, `__reactProps$` など）
  - イベントリスナーの有無
  - 要素の位置・サイズ（`getBoundingClientRect`）
  - スクロール位置、ビューポートサイズ
  - コンソールエラー・警告の有無
- 出力は構造化する: JSON で出力し、セクションごとにラベルをつけ、呼び出し者がコピペしやすくする

#### スワイプ・ドラッグ・スクロールなど連続的な操作が関わるバグの場合

静的なスナップショットでは状態の変化を捉えられない。以下のようなポーリングログスクリプトを提案する:

- **0.5秒間隔**で状態をログ出力する（`setInterval`）
- **5〜10秒で自動停止**する（`setTimeout` で `clearInterval`）
- 出力形式は **JSON ではなく、1行にまとめたフラットな文字列** にする（コンソールからのコピーが楽）
  - 例: `[0.5s] touchActive=true scrollY=120 translateX=-45px transition=none pointerEvents=auto`
- 呼び出し者に「スクリプトを実行したら、すぐに操作（スワイプ等）してください。数秒でログが止まります」と伝える
- ログ出力が終わったら、コンソールの出力をまとめてコピペしてもらう

スクリプトを提示し、呼び出し者にブラウザの DevTools コンソールで実行してもらい、出力を貼り付けてもらう。

### 3. 並列調査（playwright-cli）

playwright-cli を使う場合、呼び出し者へのスクリプト実行依頼と並列して以下を行う:

- 同じページにアクセスし、同様の状態を再現する
- DOM の状態やスクリーンショットを取得する
- 呼び出し者から得た情報と突き合わせて差異がないか確認する

### 4. 原因の仮説提示と動作確認

コンソール出力と playwright-cli の結果を突き合わせ、ソースコードを追って原因の仮説を立てる。

- 得られたランタイム情報から、関連するソースコードを Grep / Read で追う
- 状態管理（store, context, state）の流れを追う
- CSS の優先度・継承関係を確認する
- 情報が不足していれば、追加のコンソールスクリプトを依頼する（ただし最小限に）

**重要: 勝手に「原因を特定した」と断定して修正に進まないこと。**

- 仮説を呼び出し者に提示し、修正案を説明する
- 修正を適用したら、呼び出し者に実際のブラウザで動作確認してもらう
- 呼び出し者が「直った」と確認するまで、次のステップ（再発防止等）に進まない
- 直っていなければ、追加調査を行う（仮説が間違っていた可能性を素直に認める）

### 5. 再発防止と自動テスト化

修正して終わりではない。以下を必ず検討し、実行可能なものは実施する。

#### なぜ playwright-cli だけで機械的に検証できない状態になっているのか？

- playwright-cli で再現できなかった場合、その理由を明確にする
  - 認証・セッション状態の問題？
  - 特定のデータ依存？
  - タイミング依存（race condition）？
  - ブラウザ固有の挙動？
- その障壁を取り除くことはできないか？（テスト用のシード・フィクスチャ、認証バイパスなど）

#### 自動テスト化の検討

- E2E テスト: playwright-cli や Playwright Test で再現テストを書けないか？
- UI の位置・割合のテスト: 完全なピクセルパーフェクトでなくても、以下のような「当たり前の位置関係・割合」をアサートできないか？
  - 要素が画面内に収まっている（`boundingBox` がビューポート内）
  - 要素同士の上下左右の位置関係が正しい（A は B の上にある、など）
  - 要素のサイズが妥当な範囲にある（幅が親の 50% 以上、など）
  - 要素が重なっていない / 意図的に重なっている
  - スクロールなしで見える位置にある
- Visual Regression Test: スクリーンショット比較で検出できないか？
- コンポーネントテスト: Storybook + Testing Library で状態ごとの表示を検証できないか？
- デバッグ用操作関数の注入: 再現しにくい UI 操作（ドラッグ、リサイズ、複雑なインタラクション等）を、コンポーネントのノードにデバッグ用フィールドとして関数を生やし、テストから直接呼び出せるようにできないか？

上記は例示であり、これらに限らず状況に応じてさらに考えること。モダンな手法や geek 的なアプローチがないか調査すること。

#### メタレベルの再発防止

- CLAUDE.md の更新: 今回の教訓を反映すべきか？（例: 「この種の UI バグは playwright-cli で検証すること」「コンソールスクリプトのテンプレート」など）
- 開発プロセスの改善: レビュー時のチェック項目追加、Storybook のバリエーション追加など
- 型・構造による防止: CSS の制約（CSS Modules の命名規約、design token の強制）、コンポーネント API の型制約など
- CI への組み込み: 今回書いた E2E テストや Visual Regression Test を CI に追加できないか？
- デバッグ操作関数のルール化: 複雑な UI 操作を伴うコンポーネントには、テスト・デバッグ用の操作関数を必ず生やす仕組み・ルールを導入できないか？（lint ルール、コンポーネント設計テンプレート等）

上記は例示であり、これらに限らず状況に応じてさらに考えること。モダンな手法や geek 的なアプローチがないか調査すること。

### 6. タスク管理

- 修正内容をタスクとして記録する
- 長期的な改善（テスト基盤強化、playwright-cli 環境整備など）は別タスクとして切り出す
- 再発防止策の実施状況を追跡可能にする

### 7. 報告

修正内容を報告する:

- 症状: 何が起きていたか
- 原因: ランタイム上で何が問題だったか（コンソール出力の何が決め手だったか）
- 修正: 何をどう直したか（ファイル:行番号 付き）
- 自動テスト: 追加したテスト、または追加できなかった理由
- 再発防止: 実施した対策と未実施の提案
- playwright-cli 検証状況: 機械的検証の可否と、できない場合の障壁
