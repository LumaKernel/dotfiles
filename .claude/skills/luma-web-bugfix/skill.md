ローカル環境でバグを再現し、原因を特定して修正する。修正後はテスト・型チェック・lint を通し、リグレッションがないことを確認する。さらに、バグが混入した根本原因を掘り下げ、構造的・仕組み的な再発防止策を講じる。

## 入力

ユーザーからバグの説明を受け取る。以下の情報があれば活用する:
- 再現手順、エラーメッセージ、スクリーンショット
- 該当ファイル・コンポーネント名
- 期待する動作 vs 実際の動作

情報が不足していれば質問して明確にする。

## 手順

### 1. 現状把握

- `git status` / `git diff` で未コミット変更を確認（既存の作業を壊さない）
- 関連ファイルを特定し読む（エラーメッセージ、コンポーネント名、ファイルパスから）

### 2. バグ再現

再現方法をバグの種類に応じて選ぶ:

- **テストで再現可能**: 失敗するテストを書く（またはテスト実行で確認）
  ```bash
  npm test -- <対象ファイル>
  ```
- **型エラー**: `npx tsc --noEmit` で確認
- **lint エラー**: `npx eslint <対象ファイル>` で確認
- **実行時エラー**: dev server (`npm run dev`) や Storybook (`npm run storybook`) を起動して確認
- **再現スクリプトが必要な場合**: `./repro.ignore.ts` にshebang付きで作成し、chmod → 実行を分けて行う（`&&` で繋がない）

再現できたら、再現手順・エラー内容を明確に記録してからfixに進む。

### 3. 原因特定

- エラーのスタックトレース、型エラーメッセージを読む
- 関連コードを Read / Grep で追う
- 直近の `git log` / `git diff` で最近の変更が原因か確認
- 必要に応じて Agent (Explore) で広範囲の調査

### 4. 修正

- 最小限の変更で修正する。余計なリファクタリングはしない
- プロジェクトの規約を守る:
  - `as` キーワード禁止、type guard を使う
  - `readonly` 全フィールド、`type` over `interface`
  - exhaustive check (assertNever)
  - template literal 内で `satisfies` 使用

### 5. 検証

すべて通ることを確認する:

```bash
# 型チェック
npx tsc --noEmit

# lint
npx eslint

# テスト（対象ファイルのみ先に）
npm test -- <対象ファイル>

# 全テスト
npm test
```

1つでも失敗したら、修正を見直す。

### 6. 根本原因分析と再発防止（最重要）

バグの修正だけで終わらない。以下の観点で**無制限に**掘り下げる:

#### なぜこのバグは混入したのか？

- **git blame / git log**: いつ、どのコミットで混入したか特定する
- **コミット差分の振り返り**: その変更を最初から正しくするにはどうすべきだったか
- **レビューで見落とした理由**: 変更の影響範囲を見誤ったか、テストが不足していたか

#### なぜ既存の仕組みで防げなかったのか？

- **型システム**: TypeScript の型で検出できなかったか？ より厳密な型定義にできないか？
- **exhaustive check（2種）**:
  - `assertNever`: union型 / switch分岐の網羅性。新しいバリアントが追加されたとき、対応漏れをコンパイルエラーにする
    ```ts
    switch (action.type) {
      case "open": ...
      case "close": ...
      default: assertNever(action.type);
    }
    ```
  - `assertRestExhaustive`: オブジェクトのプロパティ網羅性。全フィールドを分割代入で使い切り、残りが空であることをアサートする。プロパティ追加時に対応漏れをコンパイルエラーにする
    ```ts
    const { name, score, ...rest } = pass;
    assertRestExhaustive(rest);
    // → pass に新フィールドが追加されたら rest が空でなくなり型エラー
    ```
- **テスト**: このケースをカバーするテストがなぜなかったか？ テスト戦略に穴はないか？

#### 仕組みとしてどう防ぐか？（ここが本質）

以下を検討し、実行可能なものは修正と一緒に実装する:

- **eslint ルールの追加**: 既存ルールの設定変更で防げないか？
- **eslint カスタムルールの作成**: 既存プラグインにないパターンなら、`@luma-dev/eslint-plugin-luma-ts` への提案や、プロジェクトローカルのカスタムルール作成を検討
- **tsconfig の厳格化**: `noUncheckedIndexedAccess` のような厳密フラグで防げないか？
- **型レベルの制約追加**: branded type、template literal type、conditional type で不正な値を型レベルで排除できないか？
- **コードコメントでの明記**: 変更時に一緒にすべきことをコメントで強制できないか？（例: `// この型を変更したら X も更新すること`）
- **テストの構造化**: このパターンのバグを自動検出するテストヘルパーやテストパターンを追加できないか？
- **アーキテクチャ・構造の改善**: モジュール分離、レイヤリング、依存方向の見直しで、そもそもこの種のバグが発生しにくい構造にできないか？
- **メタ戦略の更新**: design/ 配下の設計文書やCLAUDE.md に、今回の教訓を反映すべきか？

#### 分析結果の記録

- 根本原因と再発防止策を明文化する
- 設計文書やコードコメントへの反映が必要なら実施する
- 新しい規約やパターンが生まれたら design/ 配下に記録する

### 7. 報告

修正内容を報告する:
- **原因**: 何が問題だったか（1-2文）
- **修正**: 何をどう直したか（ファイル:行番号 付き）
- **根本原因**: なぜ混入し、なぜ防げなかったか
- **再発防止**: 実施した仕組み的対策（型制約、eslintルール、テスト追加、設計文書更新など）
- **未実施の提案**: 今回は実施しなかったが検討した対策（eslintプラグイン作成など大きなもの）

コミットはユーザーに確認してから行う（勝手にコミットしない）。
